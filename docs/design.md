# sagasu 設計ドラフト

- 状態: ドラフト v0(2026-07-27)
- 対象読者: 自分自身+開発エージェント。実装前の合意形成用

## 1. 背景と課題

フォルダ管理に規律を要求する探索モデルは破綻している。ファイルは「置いた場所」ではなく「意味」で思い出すのに、ファイルシステムは場所でしか引けない。既存の解決策はそれぞれ片翼しかない:

- Everything 系: ファイル名は爆速で引けるが、内容・意味は見えない
- OS 標準検索 (Windows Search / Spotlight): 遅い・不透明・カスタマイズ不能
- LLM ベースの整理ツール: コストと速度が実用ラインに乗らない。全ファイルへの適用は非現実的

sagasu は「rg 級に速い決定的なコア」+「機械生成の意味レイヤー」+「検索時差分マージによる鮮度の透過化」の組み合わせでこの隙間を埋める。

## 2. コンセプト

1. **CLI ファースト**。rg と同じく、まず単体で便利な CLI として成立させる。GUI(Tauri)はその上のフロントエンド
2. **決定的・オフライン・高速**。コア機能はネットワークもモデル推論も要求しない。同じ入力に同じ出力
3. **インデックスは古くてよい**。鮮度は検索時の差分マージで補償する(§5)。これが本ツールの中心的な設計判断
4. **意味はプログラムで作る**。タグ・ファセットはルール+統計で機械生成。LLM / embedding はプラグイン境界の外(§6, §8)
5. **台帳になれるスキーマ**。将来のティアリングサービス(§9)を見据え、v0 からコンテンツハッシュ・安定ID・アクセス履歴を持つ(§7)

### 非目標 (non-goals)

- Explorer / Finder を置き換えるファイルマネージャではない(移動・コピー等のファイル操作はスコープ外)
- クラウド同期・バックアップはコアの責務ではない(将来のサービスレイヤー)
- v0 では LLM・embedding を必須とする機能を持たない
- shiori とはコードベースも責務も独立(shiori = リポジトリ知識、sagasu = ローカルファイルシステム)

## 3. 全体アーキテクチャ

```
┌────────────────────────────────────────────────┐
│ UI (Tauri / Web 技術)              …後段       │
├────────────────────────────────────────────────┤
│ CLI (rg 風 UX)                                 │
├────────────────────────────────────────────────┤
│ クエリパイプライン                              │
│   検索(索引) ⊕ 差分ライブスキャン → マージ      │
├──────────────┬─────────────────────────────────┤
│ 索引ストア    │ インデクサ(パイプライン4段)     │
│  SQLite      │  1. メタデータ走査(全件・高速)   │
│  tantivy     │  2. 本文抽出(対象形式のみ)       │
│  (sqlite-vec)│  3. embedding      …プラグイン   │
│              │  4. LLM タグ付け    …プラグイン   │
├──────────────┴─────────────────────────────────┤
│ FS 監視/差分源: USN Journal / FSEvents /        │
│                fanotify / mtime フォールバック   │
└────────────────────────────────────────────────┘
```

### 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| コア言語 | Rust | 速度・単バイナリ配布・クロスプラットフォーム。必要部品が揃っている |
| ディレクトリ走査 | `ignore` クレート | rg の並列走査そのもの(※既定のフィルタは全部切る — §4-1) |
| FS 監視 | `notify` クレート | ReadDirectoryChangesW / FSEvents / inotify の抽象化 |
| Windows 初回スキャン | MFT / USN 直読み | Everything 方式。数百万ファイルでも数秒〜数十秒 |
| 全文索引 | tantivy | Rust 製 Lucene 相当。大規模時の性能が FTS5 より良い |
| 日本語トークナイズ | Lindera | tantivy に公式接続。trigram より精度が出る |
| メタデータ/タグ | SQLite | 単一ファイル・組み込み。将来 sqlite-vec を同居可能 |
| ハッシュ | BLAKE3 | 高速。重複検出・同一性追跡の基盤 |
| UI | Tauri | コアが Rust ならそのまま接続。Web 技術で可視化が書ける |

tantivy vs SQLite FTS5 は**ベンチで確定した(tantivy 継続)**。10万ファイル規模の実測と根拠は §11。

**CLI 層の体系(サブコマンド・引数・出力形式・設定ファイル・終了コード)は
`docs/cli.md` が正本**(issue #6)。機械可読出力 `--json` の位置づけもそこに書いてある —
**M4 Tauri UI はコアに直接リンクするので、`--json` は M4 のための契約ではない**。
読者はシェルスクリプト・他ツール・エージェントで、プロセス境界の向こう側にいて
Rust でリンクできない相手だけ。

## 4. インデクサ(パイプライン4段)

段ごとに処理コストが1〜2桁違うため、全ファイルに全処理をかけない。

1. **メタデータ走査(全件)**: パス・拡張子・サイズ・タイムスタンプ・マジックバイト。初回はフルスキャン(Windows は MFT)、以降は差分源(§5)からの変更リストのみ処理
2. **本文抽出(対象形式のみ)**: テキスト/コードはそのまま。PDF・Office は専用ライブラリで抽出(IFilter は品質がまちまちなので採らない)。サイズ上限・形式許可リストで制御
3. **embedding(プラグイン・既定無効)**: §8
4. **LLM タグ付け(プラグイン・既定無効)**: §8

インデックス作成は定期実行(スケジューラ or 常駐 watch)。**インデックスの完全性より走査の速さを優先**し、取りこぼしは §5 の差分マージと低頻度のフルスキャン(整合性チェック)で回収する。

### 4-1. 索引スコープ:既定の除外規則(issue #14 の確定事項)

§11 の open question「既定の除外規則」への回答。利用者向けの説明は
`docs/index_scope.md`。実装は `sagasu-core::walk::ExcludeSet`。

**gitignore と hidden の継承は誤り** — §3 の技術選定は `ignore` クレートの利点として
「gitignore 互換の除外規則が無料で付く」と書いていた。これは検索エンジンの既定としては
誤りで、実測でそう出た(issue #14、2026-07-29 Windows 実機)。

| 対象 | クレート既定 | 実体 |
|---|---|---|
| 95ファイルのコーパス | 35 | 95(`.opencode/` `.github/` の md 19件が黙って消えた) |
| `C:\Users\` | 494 | 151,674(0.3%) |

gitignore の除外規則は「バージョン管理に入れるべきでないもの」の定義であって
「検索できなくてよいもの」の定義ではない。よって **`WalkBuilder` の既定フィルタは
5つすべて明示的に切り**(`hidden` / `ignore` / `git_ignore` / `git_global` /
`git_exclude`)、除外セットを独立に定義する。残すのは**ビルド生成物とキャッシュ**だけ
— 量が多く、意味が薄く、索引されている別のもの(ソース)から再生成できる。

**ドットディレクトリは除外しない。** hidden 属性(Windows の `FILE_ATTRIBUTE_HIDDEN`)と
先頭ドット(Unix の命名規約)は**別物として扱う**。前者は opt-in の `--skip-hidden` が
読む実在の属性で、後者はどのプラットフォームでも hidden とみなさない。したがって
`--skip-hidden` は Unix では常に何もしない(Unix に hidden 属性が無いため)。
実機検証はできないので、属性ワードの判定(`walk::hidden_from_attributes`)を
プラットフォーム非依存の純関数として切り出し、両 OS で走る単体テストで固定した。

**`.gitignore` は採用する。ただし opt-in で、ルート1枚の、ディレクトリ規則だけ。**
`--use-gitignore` で有効。絞る理由は、gitignore がディレクトリを外す意味はほぼ一意で
「この下は生成物」だが、**ファイル**を外す意味は生成物・秘密・ローカル専用の3つあり、
後ろ2つ(`.env` `TODO.md`)は自分のディスクを検索する動機そのものだから。
ネストした `.gitignore` / `.git/info/exclude` / グローバル gitignore は読まない。
ファイルが無いのは規則0件、**あるが壊れているのはエラー**(頼んだのに黙って
効かないのが最悪)。

**除外セットは1つ、そして索引がそれを持つ** — §5-1 の「クロールと差分の除外は同一セット」を、
`meta.exclude_policy` への保存と復元で実際に1つにした。§5-2 の残論点
「クロールの `--exclude` の再現」はこれで解消。対称に効く論点で、差分側の規則が
緩いと**索引に行が無いファイルがライブヒットとして答えに出る**(欠けるの逆側)。

保存するのは規則の**在り処ではなく規則そのもの**。`.gitignore` の行はクロール時に
policy へ写す。参照にとどめた版は実測で2通りに壊れた:索引後にファイルを壊すと
全クエリが exit 1 になり、消すと規則0件に縮んでクロールが刈ったディレクトリが
ライブヒットとして復活した。索引は自分が使った規則を所有する。
逆に**復元できない規則は書かせない** — 改行を含む除外名はクロール前に拒否する
(通すと「成功報告付きの索引全損」になる)。`decode` の未知キー・未知バージョンは
エラーで、前方互換は版番号の担当。読めない policy が検索を殺さないのは、
クエリ側が index-only へ degrade して stale notice を出すため。

**除外は数え上げる。読めなかったものは別に数える** — 除外ディレクトリの中身も
walk して数える。速度と引き換えに「何件消えたか言えない除外」を作らないため。
開けなかったディレクトリ・stat できなかったファイルは**除外ではない**ので
`errors` として別に数える(誰も落とせと言っていない)。
`scanned = indexed + skipped + errors` が恒等式で、`sagasu index` は規則別の内訳と
`unreadable :` を、`sagasu status` は規則そのものと直近クロールのエラー件数を出す。

**実測 — これは「プロトタイプ → 本実装」であって「main → 本 PR」ではない**

比較対象を取り違えないこと。ドットディレクトリの索引・`hidden(false)`・
`git_ignore(false)` は M0〜M1 の時点ですでに入っており、**このリポジトリを
コーパスにすると main と本実装の索引件数は完全に一致する**。下の表の「旧既定」は
issue #14 が実測した当時のプロトタイプ、すなわち `ignore` クレートの既定のままの
walker であって、直前のリリースの挙動ではない。

計測は 2026-08-07、release、Linux / ext4。

| コーパス | 走査対象(全フィルタ off) | プロトタイプ既定 | 本実装の既定 | 差 |
|---|---|---|---|---|
| sagasu リポジトリ自身 | 14,349 | 69 | **75** | +6 |
| `/usr` | 68,134 | 67,825 | **63,901** | −3,924 |

リポジトリでの +6 は `.github/workflows/*.yml` 2件、`.gitignore` 3件、
`prototypes/.cargo/config.toml` の計6件で、**プロトタイプ既定ではこのリポジトリの
CI 定義が索引から丸ごと落ちていた**。`/usr` は集合で見ると足し引きの両方が起きている:
本実装はプロトタイプ既定が隠していた 309 件(`.build-id/` 273、`.hidden/` 8、
`.registry/` 6 ほか)を回収し、代わりに `__pycache__` 4,209 件と `venv` 24 件を
意図的に落とす。「件数が多い方が良い」ではなく「規則の軸が違う」が正しい読み方。

**では issue #14 の作業で何が変わったのか** — 索引**対象**ではなく、
索引対象の**決め方と説明可能性**:

1. 除外規則を独立の型として定義し、`--skip-hidden` / `--use-gitignore` という
   opt-in の軸を足した(既定は従来どおり)
2. その規則を索引に保存し、検索時の差分照会が同じものを復元する。
   これがないと `--exclude` を付けたクロールは以後の全クエリと食い違う
3. 除外・走査エラーを規則別に数えて表示し、`scanned` の恒等式を成立させる
4. 上の判断を docs に書き、実装と一致させる

### 4-2. 本文抽出の対象判定(issue #15 の確定事項)

§11 の open question「本文抽出の対象形式の初期セットとサイズ上限」への回答の前半。
実装は `sagasu-core::text`。

**拡張子は入口であって判定ではない** — 固定リストだけで決めると、リストに無い
プレーンテキストがエラーも警告もなく消える(実測: `mjs` の欠落で 41 ファイル、
残ったのは `indexed files : 35` という数字だけ)。判定は3段にする:
拡張子の許可リスト(開かずに採用)→ 拡張子の拒否リスト(開かずに却下)→
**先頭512バイトの内容サンプリング**。3段目があるので `Makefile` や `.tmpl` のような
「誰もリストに足さなかったプレーンテキスト」が索引に入る。

判定の優先順位は速度の順であり、同時に**証拠の強さの順ではない**ことに注意する。
拡張子が許可リストに載っていれば内容は見ない。これは「拡張子を偽ったテキスト」を
取りこぼさないための選択で、逆に「`.csv` を名乗るバイナリ」は素通りする。
`tags::classify` の `anomaly:format-mismatch` が §6-1 の通り
「拡張子がバイナリ形式を主張している」場合だけを見るのと同じ非対称を、
同じ理由で採っている。

**判定の共有方向** — issue #15 は「タグエンジンの形式判定を索引対象の決定にも使う」
ことを示唆していたが、実装は**逆向き**にした。`tags::classify` が `crate::text` を
呼ぶ。理由は、`format:text` の意味を「全文索引が本文を取ったはずのもの」に
一致させたいから。逆向きにすると、タグ側のマジックバイト表(形式名を増やすたびに
1行ずつ伸びる)が本文抽出の可否を左右し、表の追加が索引対象を静かに変える。

**許可リストはユーザーが広げられる** — `--ext` と設定ファイル `sagasu.toml` の
`[text]` セクション(`--config` で明示可)。形式は TOML、未知のキーはエラー
(`text_exts` と打ち間違えた設定が「読めたが何もしない」になると、利用者は
sniffer を疑う)。

**設定ファイルは 1 本に統合した**(issue #6、詳細は `docs/cli.md` §5)。
当初は `sagasu-text.toml`(本文抽出) と `sagasu-tags.toml`(タグルール) の 2 本で、
理由は「`sagasu-tags.toml` を読むのは `sagasu tag` であって `sagasu fulltext` では
なく、片方のコマンドが "tags" という名前のファイルから本文抽出の設定を読むのは
説明がつかない」だった。**この懸念はセクション名で解消される** — `[text]` と
`[[tags.rule]]` に分かれていれば、どちらのコマンドが何を読むかはファイル名ではなく
セクション名が説明する。一方で 2 本立ての代償(探索パス 2 つ・フラグ 2 つ・
「どちらに書くのか」を利用者が毎回思い出す)は消えない。**PoC 段階で利用者は
いないので旧 2 ファイルの後方互換は持たないが、置かれているのを検出したら
統合された旨のエラーで案内する**(黙って無視すると、利用者から見えるのは
「ルールが効かなくなった」だけになる)。

**判定規則も索引が持つ** — 除外規則とまったく同じ理由で、`sagasu fulltext` は
使った規則を `meta.text_policy` に書き、`sagasu search` はそこから復元する。
設定ファイルの自動探索(cwd の `sagasu.toml`)だけに頼っていた版は、
**別ディレクトリから検索すると探索が空振りして組み込みリストに戻り**、
ライブ grep が索引と違う判定をした。その結果は「編集した瞬間そのファイルが
答えから消える」— 索引ヒットは変更として落ち、ライブヒットは生まれない。
呼び出し側が `--ext` を明示すれば勝つ(構築済みの索引に対する逃げ道として要る)が、
索引の規則と食い違えば警告を出す。`sagasu search` は使った規則を必ず表示する。

**除外は件数と理由、さらに拡張子の内訳を出す** — 理由別の件数だけでは
「41件落ちた」までしか言えないが、拡張子別の内訳を添えると `.mjs: 41` と出て
**足すべき引数がそのまま読める**。`candidates = indexed + skipped` が常に成立する。

**判定の既定の細部** — ESC (0x1B) は制御文字として数えない(ANSI 色付きのログは
人が探す対象)。制御文字比率の分母には 512 バイトの下限を置く(無いと 40 バイトの
ファイルが制御文字1個で binary になる)。

**対象0件は警告** — `index` / `fulltext` はどちらも stderr 警告+終了コード 2
(issue #49 で 1→2。正本は docs/cli.md §6)。
加えて `sagasu status` が後からでも同じことを言う(ビルド時の警告は流れる):
クロール無し / live 0件 / 全文索引はあるのに 0 文書、の3つに警告を出す。
「索引したが引けない」と「そもそも索引していない」がユーザーから区別できないのが、
検索エンジンとして一番たちが悪い失敗。

**実測 — §4-1 と同じ注意。これは「プロトタイプ → 本実装」の比較**

`mjs` を含む拡張子リストも内容サンプリングも M1 の時点で入っている。下の「旧」は
issue #15 が実測した当時のプロトタイプの 33 種固定リストであって、直前のリリースの
挙動ではない。計測は 2026-08-07、release、Linux / ext4、どちらも同じ既定除外セット後、
0 バイトと 2MiB 超は除く。

| コーパス | 候補 | プロトタイプ(33種) | 本実装 合計 | うち拡張子 | うち sniff | 差 |
|---|---|---|---|---|---|---|
| sagasu リポジトリ自身 | 75 | 68 | **74** | 68 | 6 | +6 |
| `/usr` | 63,570 | 36,680 | **55,914** | 45,739 | 10,175 | **+19,234** |

`/usr` の +19,234 件の内訳上位は `.svg` 5,615、拡張子なし 3,055、`.vim` 1,629、
`.s` 1,256、`.pl` 1,206、`.cmake` 1,063。拡張子なしの 3,055 件は
**拡張子リストをどれだけ伸ばしても届かない集合**で、3段目の存在理由そのもの。
プロトタイプの判定はこのコーパスの本文対象の 34% を黙って落としていた。

**issue #15 の作業で変わったのは判定そのものではなく、判定の可搬性と説明可能性**:
設定ファイルによる拡張、判定規則の索引への保存(下記)、除外の拡張子別内訳、
`sagasu status` の空振り警告。

### 4-2-1. PDF/Office の本文抽出(issue #40 の確定事項)

§4-2 の3段判定に**4段目ではなく 3.5 段目**を足した。判定の並びは
許可リスト → **抽出器の照会** → 拒否リスト → 内容サンプリング。実装は
`sagasu-core::docmeta`、判定は従来どおり `text::TextPolicy::classify_ext` の**1箇所だけ**で、
`ExtVerdict::Extract(BodyFormat)` が「どのパーサを使うか」まで持って返る。
呼び出し側が拡張子から導出し直す経路は無い。

**拡張子は拒否リストにも残したまま** — 冗長ではなく、これが feature OFF 時の縮退そのもの。
`office` / `pdf` を落とすと `BodyFormat::from_ext` が何も返さず、そのまま拒否リストに落ちて
`unsupported format` に計上される = #40 以前の挙動。**黙って消えることは無い**。

**選定** — 依存の重さを実測して決めた(issue #40 のコメントに全表)。
docx/xlsx/pptx は `zip` + `quick-xml` の自前配線(3形式 + `docProps` が1系統で済む)、
PDF は `lopdf`(`default-features = false`)、EXIF は `kamadak-exif`。
**`pdf-extract` を採らなかったのは精度ではなく panic** — Identity-H 以外の定義済み CMap 名
(`UniJIS-UCS2-H` 等、日本語 PDF が実際に使う)で無条件 panic する。ディスク全体を走る
プログラムにとってそれは品質のトレードオフではなく落ちるということ。
`zip` は `deflate-flate2-zlib-rs`(= `deflate` から zopfli を抜いたもの)。zopfli は圧縮器で、
インデクサは一度も呼ばない。

**それでも panic は捕まえる** — `docmeta` の入口は全て `catch_unwind` で包み、panic は
**メッセージ付きの Err** に変換する。「今は Result を返す」はコードの現状であって保証ではない。

**台帳は不変** — `candidates = indexed + skipped` は抽出経路でも成立する。抽出失敗は
`SkipReason::ExtractFailed`(`unsupported format` とは**別の理由**)に計上し、先頭数件は
**パスと理由をそのまま**サマリに載せる。「この形式は読まない」と「読める形式だがこのファイルが
壊れている」は利用者の取るべき行動が違い、混ぜると抽出器の退行が期待値の大きい数字の中に隠れる。

**サイズ上限は既存の枠組みのまま** — `--max-size`(既定 2 MiB)が抽出出力の上限でもあり、
展開後サイズの上限でもある。超えたら**打ち切って返す**(失敗にしない)。300ページの PDF の
先頭2MiBが引けるのは、文書ごと消えるよりましだから。

**ライブ側も同じ判定を通す** — `fresh::read_body` に同じ `Extract` 経路がある。無いと
「docx を編集した瞬間その文書が答えから消える」(索引ヒットは変更として落ち、ライブヒットは
生まれない) — §4-2 が `text_policy` を索引に保存した理由と同じ穴を、新形式で開け直すことになる。

**既知の限界(継承)** — `ToUnicode` を持たない古い PDF は Rust エコシステム全体で正しく
読めない。`.doc` / `.xls` / `.ppt` / OpenDocument / `.rtf` は拒否リストのまま(別形式であって
別拡張子ではない)。

## 5. 鮮度設計: 検索時差分マージ

本ツールの独自性の中核。「インデックスの古さ」をユーザーから見えなくする。

1. インデックス作成時に**時点マーカー**を記録する(Windows: USN 番号、その他: 走査開始時刻)
2. 検索時、まず差分源に「マーカー以降に変更されたファイル一覧」を問い合わせる
   - Windows: USN Journal のレンジ読み(ジャーナル読みなので数十 ms 級)
   - macOS: FSEvents / Linux: fanotify(常駐 watch が前提)
   - フォールバック: 対象ルートの mtime スキャン(遅いが確実)
3. 差分集合(通常は全体の 0.1% 以下)だけを rg 方式でライブ grep +メタデータ再取得
4. 残りはインデックスから返し、結果をマージ。削除済みファイルはインデックス結果から除外、変更ファイルはライブ結果で上書き

差分集合が閾値を超えた場合(例: インデックスが極端に古い)は、ライブスキャンを打ち切って「インデックスが古い」と明示し、再索引を促す。

### 5-1. M2 実装の確定事項

M2(issue #3 / #16)で上記を実装した。実装は `sagasu-core::delta`(差分源)と
`sagasu-core::fresh`(マージ)に分かれる。以下は実装で確定した設計判断。

**マーカー** — `meta.delta_marker` に1行で保存する(`docs/schema_v0.md` 参照)。

| 種別 | 内容 | 失効 |
|---|---|---|
| `mtime` | 走査開始時刻(unix ns) | しない |
| `usn` | ボリューム / **journal id** / NextUsn / MaximumSize / 取得時刻 | する(下記) |

USN マーカーには journal id と MaximumSize を必ず含める。前者はジャーナル再作成で
USN 番号空間ごと無効になるため番号比較だけでは不十分だから、後者はマーカーの
残り寿命を見積もるため。USN は「ジャーナル内のバイトオフセット」なので、
`(現在の NextUsn − マーカーの NextUsn)` がそのまま消費バイト数になり、
`MaximumSize` との差と経過時間から残り秒数が概算できる(`delta::estimate_lifetime`)。

**差分照会の3つの結果** — 「取れた/取れない」の2値ではなく3値にした。

- `Complete`: 差分集合は完全
- `Truncated { limit }`: 閾値超過で打ち切り。集合内の項目は正しいが取りこぼしがある
- `RescanRequired(reason)`: 差分そのものが判定不能。全再走査以外に回復手段がない
  - `marker < first_usn` / `ERROR_JOURNAL_ENTRY_DELETED` / journal id 不一致 /
    ジャーナル利用不可 / マーカー未記録

打ち切りと失効を独立の分岐として持つのは、対処が違うから(前者は閾値を上げれば
済むことがある、後者は絶対に済まない)。USN ジャーナルはリングバッファで、実測で
数分に 8MiB 消費するため、マーカー失効は障害ではなく通常運用で起きる(issue #16)。

**除外セットは1つ** — クロールの `ExcludeSet` を差分集合にもそのまま適用する。
USN はボリューム全域のレコードを返すため、これを掛けないとテレメトリ(`.etl`)や
PowerShell 一時ファイルで差分集合が埋まる。除外件数は集計して表示する
(20k ファイルのツリーにビルド生成物ノイズを混ぜた実測で 98% が除外側)。

**削除の扱い** — 削除は差分源からは来ない。mtime 走査は「今あるもの」しか見えない
ため、削除はマージ側でインデックスヒットの存在確認として処理する。確認対象は
ヒット件数(数十)であってコーパス規模ではないので、これでフォールバック経路も
「速いだけでなく完全」になる。USN は削除レコードを返すが、同じ経路に合流させる。

**マージ結果の並び** — インデックス側は BM25、ライブ側は term 出現数で、両者の
スコアは比較可能ではない。捏造した共通スケールで混ぜるのではなく、
ライブヒットを先頭に置き、`HitOrigin` でどちら由来かを常に表示する。
ただし先頭に置くことと1ページを占有することは別で、インデックスヒットが
存在する限りライブ側は `--limit` の半分までとする(でないと、ありふれた語 +
午前中の編集だけでランキング結果がページから消え、鮮度補正が検索の置き換えになる)。

**差分集合キャッシュ(GUI インクリメンタル検索の中核論点)** — 実装した
(`delta::DeltaCache`)。1キーストロークごとに差分照会を走らせると、mtime 経路では
毎回ルート全体の `stat` 走査になり、鮮度機構そのものが UI を遅くする。無効化条件は
2つだけ:

1. **TTL 経過**(既定 1000ms)。鮮度を有界に犠牲にしてレイテンシを買う。
   打鍵の連射は1回の照会を共有し、他ウィンドウでの変更は1秒以内に見える
2. **マーカー変化**。再索引でマーカーが動くと、旧マーカー基準の差分集合は
   全項目が無意味になる。期限切れとは別カウンタで数える(正当性の無効化なので)

明示破棄 `invalidate()` も持つ(自分でファイルを書いた直後に TTL を待つ理由はない)。
プロセスをまたぐ永続キャッシュは採らない: 復元後にどのみちファイルシステムと
突き合わせる必要があり、それは再計算と同じコストになる。

**計測(この環境: Linux / ext4 / release ビルド)**

| コーパス | 差分 | index | delta | live grep | merge | 合計 |
|---|---|---|---|---|---|---|
| 20,000 files | 20 (0.1%) | 2.2ms | 32.5ms | 0.7ms | 0.15ms | 35.5ms |
| 20,000 files(同上・DeltaCache ヒット) | 20 | 2.2ms | 0.0ms | 0.7ms | 0.14ms | 3.0ms |
| 100,000 files | 100 (0.1%) | 5.4ms | 165.5ms | 1.3ms | 0.6ms | 172.8ms |
| 100,000 files(同上・DeltaCache ヒット) | 100 | 4.5ms | 0.0ms | 1.1ms | 0.6ms | 6.2ms |

ライブ grep とマージは差分規模に比例し、0.1% 規模では合計 2ms を切る。
支配的なのは mtime フォールバックの全 `stat` 走査で、コーパス規模に比例する
(20k で 32ms、100k で 165ms)。単発クエリでは体感不能だが、キーストローク毎に
走らせるには重い — これが USN 経路と `DeltaCache` の両方が要る理由そのもの。

### 5-1-1. 差分源の選択と、経路ごとの検出能力

**USN 経路は Windows の既定**(2026-08-08 に opt-in ゲートを撤去、issue #37)。
`delta::source_for` はまず USN を試し、ジャーナルが開けないとき(非NTFS・ジャーナル
無効・非管理者)は黙って mtime 走査に落ちる。`SAGASU_DELTA_SOURCE=mtime` で mtime を
強制できる(既定化後の脱出ハッチ)。Windows 以外は従来どおり常に mtime 走査。
旧既定で作られた索引は最初の検索1回だけ RescanRequired(マーカー種別不一致)になり、
`sagasu index` の再実行で回復する(実機で確認済み)。

かつて opt-in にしていた理由は「コンパイルが通るから既定にする」を一度やって壊したから。`sagasu index` は
ルートを canonicalize して保存するが、Windows の `std::fs::canonicalize` は
`\\?\C:\…` 形式(extended length path)を返す。`usn::volume_of` はドライブレターを
先頭バイトで判定していたためこれを弾き、**製品経路では USN が一度も選ばれていなかった**。
一方 canonicalize を通さない生の `C:\…` を渡していたテスト1本だけが USN に到達し、
空の差分集合を返して落ちた(PR #36 の Windows CI)。`volume_of` は修正したが、
実機未検証の経路をプラットフォーム全体の既定にするのは「検索が黙って何も返さない」
を作る手順そのものなので、実機で走らせるまでゲートを外さない。

**リネーム検出能力は経路ごとに違う**。`DeltaSource::detects_renames()` で公開し、
`DeltaSet` / `DeltaReport` を通じて CLI まで伝える。

| 経路 | リネーム検出 | 理由 |
|---|---|---|
| mtime (Unix) | ○ | `rename(2)` は mtime を変えないが `st_ctime` を必ず変える |
| mtime (Windows) | **×** | NTFS のリネームは LastWriteTime を変えず、ChangeTime は `std::fs` から取れない |
| USN | ○ | `RENAME_OLD_NAME` / `RENAME_NEW_NAME` レコードが出る |

検出できない場合、リネームされたファイルは答えから**移動するのではなく消える**
(旧パスのインデックスヒットは存在確認で落ち、新パスは誰も知らない)。
これは「該当ファイルなし」と見分けが付かないので、CLI は結果ごとに注意書きを出す。
黙って欠けるのが本設計で最も避けたい失敗なので、能力そのものを表に出す形にした。

### 5-2. M2 で残した論点

- **USN 経路の実機検証** — **完了(2026-08-08、issue #37)**。正常系4操作・rename検出・
  ~17倍高速・非管理者/ジャーナル不在の fallback・失効系のフェイルセーフを実機で確認し、
  opt-in ゲート(§5-1-1)を撤去した。FRN 解決の失敗が excluded に合流する計上問題は #57。
  当時の論点は以下(記録として残す):
  - **FRN → フルパス解決**。親 FRN を `OpenFileById` + `GetFinalPathNameByHandleW` で
    解決し、レコードのファイル名を連結する方式で実装した(削除済みファイルでも
    親ディレクトリは残っているのでこの向きにした)。実機未検証
  - **パス表記の突き合わせ**。`GetFinalPathNameByHandleW(FILE_NAME_NORMALIZED)` は
    ロング形式を返すので、ルートも canonicalize して `\\?\` を剥がした形に揃え、
    比較は NTFS に合わせて ASCII 大文字小文字を無視する(`delta::path_under`)。
    8.3 短縮名の `%TEMP%` 配下で実際に一致するかは実機で確認が要る
- **Windows でリネームが検出できない**(§5-1-1) — **USN 既定化(2026-08-08)で解消**。
  実機で rename の live hit を確認済み。mtime を強制した場合(`SAGASU_DELTA_SOURCE=mtime`)
  と USN probe が失敗する環境では従来どおり「リネームされたファイルは再索引まで答えから
  消える」が仕様
- **マーカー寿命の能動的な警告**。`estimate_lifetime` は用意したが、
  `sagasu status` は現在の NextUsn を取りに行かない(read-only を保つため)。
  **設計は `docs/cli.md` §9-1 で確定した**(オプトインの `--check-journal`、
  既定 off、失効/残り 24h 未満で警告、照会失敗は `checked: false` + 理由)。
  実装は issue #6 のスコープ外で、Windows 実機での確認も残件
- ~~**クロールの `--exclude` の再現**~~ → 解消(§4-1)。クロールの除外規則は
  `meta.exclude_policy` に保存され、差分側は `DeltaConfig::from_index` で復元する。
  規則を読めない索引に対しては差分照会をせず、索引のみの答えを stale として返す
  (既定へのフォールバックは、黙って別の集合を走査することと同じ)。
  この行が指していなかった側の危険も同時に消えた:
  差分側の規則が緩いと、**索引に行が無いファイルがライブヒットとして答えに出る**。
  なお **policy を持たない古い索引**は既定セットで代用する。これは推測なので
  `sagasu status` が警告を出す(旧ビルドは `--exclude` を受け付けて記録しなかった)
- **`find` のパス検索がフルスキャン**。`path LIKE '%…%'` なので 100k 行で ~50ms。
  トライグラム索引等は後続
- **差分照会とインデックス検索の並列化**。現状は逐次(計測の切り分けを優先)。
  両者は独立なので同時に走らせれば合計は max に落ちる
- **FSEvents / fanotify**。`DeltaSource` トレイトが接続点。常駐 watch が前提なので M2 外

## 6. 意味レイヤー(プログラムで作る)

### タグ生成(ルールベース)

- 拡張子・マジックバイトからの形式タグ
- パス構成要素(ディレクトリ名のトークン化)
- ファイル名パターン: 日付(`2024-03-15`, `20240315`)、版数(`v2`, `_final`, `(3)`)、スクリーンショット命名等
- 埋め込みメタデータ: Office 文書プロパティ(作成者・タイトル)、PDF info、EXIF(撮影日・機種)
- ユーザー定義ルール(パスパターン → タグ、の宣言的設定)

タグは `namespace:value` 形式(例: `format:pdf`, `date:2024-03`, `author:masuda`)で名前空間を持たせ、ファセット軸として使えるようにする。

### 6-1. M3 タグエンジン v0 の確定事項

M3(issue #4)で上記のうち埋め込みメタデータ以外を実装した。実装は
`sagasu-core::tags`(生成エンジン+格納+集計)と `sagasu-core::tagrules`
(ユーザー定義ルール)に分かれる。利用者向けの説明とルールファイルの例は
`docs/tag_rules.md`。以下は実装で確定した設計判断。

**決定性は型で守る** — 生成関数 `tags::tags_for` は
`(パス, クロールルート, 拡張子, 先頭512バイト)` だけを入力に取る純関数で、
入力を表す `FileFacts` を組み立てる以外にこの関数を呼ぶ方法がない。
時計もファイルシステムもハッシュマップの反復順も入り込む余地がないので、
再索引でタグが揺れないことが「気をつける」ではなく構造として保証される。
`mtime` は意図的にタグ源にしない(ファイルに触れるだけで動くため)。
ユーザー定義ルールも順不同(マッチした全ルールのタグの**和集合**)で、
ルールの記述順が結果に出ない。

**名前空間** — `format:` / `ext:` / `kind:` / `path:` / `date:` / `version:` /
`pattern:` / `anomaly:`、およびユーザー定義ルールが出す任意の名前空間。
名前空間と値は両方とも小文字化する。`author:Masuda` と `author:masuda` が
別バケツになるとファセットの件数が二分され、しかも外からは気づけないため。

**`format:` はマジックバイトを優先し、拡張子は次点** — schema v0 の
`files.magic`(先頭512バイト)が入力。この列は `sagasu hash` が埋めるが、
ハッシュ全体は不要なので `sagasu tag` が先頭512バイトだけを読んで
同じ列を埋める経路も持つ。実測(`/usr`, 63,901ファイル)で `format:` の付与率は
拡張子のみだと 76.4%、magic ありで 99.9%。この差は `sagasu tag` の
`magic bytes : ... missing` 行に常に出る。

**拡張子と中身の矛盾は独立の名前空間にする** — `anomaly:format-mismatch`。
ただし判定するのは「拡張子がバイナリ形式を主張している」場合だけで、
テキスト拡張子については判定しない。Shift_JIS の `.txt` が sniff できないのは
本文抽出の未対応(§4-2 / `crate::text`)であってファイルの誤ラベルではなく、
それを異常として出すと利用者はこの名前空間を無視するようになる。
`/usr` の 63,901ファイルで検出 7 件、うち誤検出 0 件(GNU ld の
リンカスクリプトなのに `.so`、先頭にプレフィクスの付いた `.zip`)。

**`path:` はディレクトリ名だけ、ファイル名の語はタグにしない** — ファイル名は
`sagasu find` と全文索引ですでに引けるが、ディレクトリ名はどこからも引けない。
ファイル名からは日付・版数・命名パターンという「解釈」だけを取る。
日付は極大な数字連なりからのみ取り(`20240315` は日付、`1234567890` は違う)、
日は捨てて `date:YYYY` と `date:YYYY-MM` の2段にする。1日1バケツの軸は辿れない。

**上限は数え上げる、そして捨てる順を決める** — 1ファイル 64 タグ、
ディレクトリは末端から 12 階層まで。上限に当たったファイル数・捨てたタグ数・
名前空間別の内訳を集計して表示する(黙って欠けさせない)。
**捨てる順は「他では復元できない情報」の逆順**で、
ユーザー定義ルール → その他の非構造タグ → `format:`/`ext:`/`kind:` → `path:`。
`path:` を最初に捨てるのは、深さに比例して増える唯一の軸であり、
かつディレクトリ名は `sagasu find` で代替できるため。同順位内は辞書順なので
全体は決定的な全順序になる。辞書順のまま truncate すると `path:` が枠を食い潰し、
ユーザー定義ルールのタグが真っ先に消えて
`sagasu tags project:client-work` が `hits: 0` を断言する(偽陰性)。

**タグ生成は全再構築・単一トランザクション** — 一部のファイルが今回の
タグ、残りが前回のタグ、という状態のコーパスはファセットの件数が意味を失う。
これは後からエラーメッセージで取り消せないので、途中失敗は全体をロールバックする。
tombstone のタグは削除する(§9 の台帳としてタグ付き tombstone を残す話は後続)。

**タグ層の鮮度は必ず表に出す。ただし「最新」とは言わない** —
`meta.tag_scan_generation` に生成時の `scan_generation` を記録し、
`sagasu status` と `sagasu tags` の両方が「N 世代遅れ」を表示する。
タグで絞り込んだ答えから新しいファイルが黙って抜け落ちるのが、
この層で最も避けたい失敗。

世代の一致だけを見て `(current)` と表示していたのは誤り(修正済み)。
`tag_scan_generation == scan_generation` は「タグ生成の後にクロールしていない」
という意味しかなく、ファイルシステムについては何も言っていない。実測で
`sagasu find` が 6 件(うち live 3 件)返すツリーで `sagasu tags <tag>` が
3 件を `(current)` と称した。**黙って欠ける**という本プロジェクト最悪の失敗に、
安心材料の見た目を与えていたことになる。現在の `sagasu tags` は
(a) タグ層が索引時点のスナップショットであることを常に明示し、
(b) 差分源に照会して「索引時点以降に変わったファイル数」を出し、
0 でなければ `fresh` の stale notice と同じ形で stderr に警告する。

**照会はするがマージはしない**のは設計判断。`find` / `search` はクエリを
ライブファイルそのものに評価できるが、タグフィルタは変更ファイル全件の
タグ生成と、ライブヒット/インデックスヒットの序列の決定を要する。
エンジンは純関数なので技術的には可能だが、それが属するドリルダウン設計は
issue #5 のスコープで、ここに半分だけ載せると微妙に異なる 2 本目の
クエリ経路ができる。よって「嘘をつかない表示」までに留める。

**ただし削除だけは照会では足りない。** §5(129-132行)の通り、差分源は
削除を報告できない — 走査は「今あるもの」しか列挙できない — ので、
鮮度設計は削除をマージの反対側、すなわち**インデックスヒットの実在確認**で
処理する。`sagasu tags <tag>` にもこれを入れた:返すページの各行を実在確認し、
消えている行は落として `dropped :` にパスごと出し、stderr に stale notice を出す。
確認対象はページ(`--limit` 件)だけなのでコストはコーパス規模に依存しない。
`hits : N of M` の M はインデックス側の件数で実在確認前の**上限値**であることも
明示する。これが無かった間、`sagasu tags kind:text` は削除済みのパスを
無警告で列挙し、同一瞬間の `sagasu find` はそれを drop していた。

**ファセット件数も live のみを数える** — `sagasu index` は tombstone を作るが
`file_tags` を作り直すのは `sagasu tag` だけなので、その間 `file_tags` には
死んだファイルの行が残る。名前空間一覧・タグ件数・タグ総数の3クエリすべてを
`files` と join して `deleted_at IS NULL` で絞る。ファセットが「3件」と提示して
ドリルダウンすると「1件」しか出ないなら、そのバケツは最初から出さない方がよい。

計測日 2026-08-07、release ビルド、Linux / ext4。

| コーパス | ファイル数 | 1つ以上のタグ | `format:` | 構造タグ以外 | 所要 |
|---|---|---|---|---|---|
| `/usr`(先頭バイトあり=既定) | 63,901 | 100.0% | 99.9% | 2.0% | 3.65s |

接頭辞の直後が区切り文字か数字)に狭めた。詳細と誤検出の実例は
`docs/tag_rules.md` §4-1。名前空間が話題に反応し始めると利用者はその軸を
無視するようになるので、ここでは再現率より適合率を採る
(`report_backup.xlsx` は意図的に取りこぼす — そのファイルは `sagasu find` で引ける)。

### ファセット階層(クラスタリングの代替)

embedding クラスタリングではなく、**タグ+パストークンの共起によるファセット階層**を動的生成する。

- 選んだタグで絞り込み → 残りの集合の中で情報量の大きいタグ軸を次の階層として提示(動的ドリルダウン)
- グループのラベルは c-TF-IDF(その集合に特徴的な頻出語)で機械生成
- 構造が決定的で安定しており、再索引でユーザーの空間記憶が壊れない

embedding ベースの「意味の地図」ビューは将来のプラグイン(§8)の上に載せる探索ビューとして検討。

### 6-3. M3 ドリルダウンの確定事項

M3(issue #5)で上記を実装した。実装は `sagasu-core::browse`(判断のすべて)と
`sagasu-cli::browse`(表示だけ)に分かれる。式の導出・実測・受け入れシナリオの
コマンド列は `docs/browse.md`。以下は実装で確定した設計判断。

**「情報量の大きい軸」= 表示できるバケツに対する期待ビット数** —
`score(ns) = H(上位 m 個の値, tail, residue)` [bit]。掛け合わせる係数は無い。
`m` は表示予算(`--values`、既定 8)で、全軸共通なのでスコアは直接比較できる。
軸の失敗はすべて低い `H` に落ちる:カバレッジの低い軸は residue バケツが巨大になり、
シングルトンだらけの軸は上位 `m` 個が 1 件ずつで tail が全部になり、
支配的な値を持つ軸は分布が偏る。**カバレッジは表示するが式には掛けない** —
residue が既にそれを表しているので、掛けると二重の罰になる。

表示予算を式に入れたのが判断の核心。値の生の分布のエントロピーだけを見ると
1,000 個のシングルトンを持つ `path:` が最大値を取るが、
その軸は「次の一手」になり得ない。逆に、集合が小さければシングルトン軸が勝つのは
**正しい**(40 件の集合で上位 8 個は 1/5 を占め、当たれば 1 件に着地する)。
実測(`/usr`, 63,901 件)で `path:` は 3,841 値を持ちながら 2.13 bit、
`ext:` の 2.73 bit に負ける。

**集合全体が共有する値は「軸」ではなく「ビュー」に載せる** — 選んでも同じ集合が
返る値は次の一手ではないのでバケツからも提示リストからも除くが、
`BrowseView::universal` に集めて必ず表示する。これを軸ごとに持たせていた版は、
**絞り込める値が 1 つも無い軸はランキングから丸ごと落ちる**ため共有値も
一緒に消えていた。1 ディレクトリに 6 枚の PNG だけ、という集合が自分について
何も言わないビューを返す — 本プロジェクト最悪の失敗の縮小版だった。

**c-TF-IDF は「文書=ファイル、語=そのタグ、クラス=絞り込み集合」** —
`W(t) = (c_S(t)/|S|) · ln(1 + N/df(t))`。ファイル名を再トークナイズせず
タグ語彙をそのまま語に使う。タグ語彙は決定的・小文字化済み・上限適用済み(§6-1)
なので、**ラベルがファセット件数と矛盾したことを言えない**。
別のトークナイザを持ち込めば「このグループは請求書」と書いてあるのに
`sagasu tags` にその軸が無い、が起こりうる。ユーザーが選んだタグ自身は除外する
(問いであって答えの説明ではない)。

**軸の順位と「次の 1 手」は別物** — 軸の順位は「どの問いを読むか」であって
「どの答えを選ぶか」ではない。値は count 降順で並ぶので、最良軸の先頭行は
**最大のバケツ = 最も絞れない値**になる。実測(`/usr`)で先頭行を辿ると
`63,901 → 21,006 → 21,002 → 21,000`(17 件まで 11 手)— 99.98% が持つ
`path:go1` は universal(厳密に 100%)ではないので除外をすり抜け、
毎回提示され続けていた。

そこで `BrowseView::recommended` を別に計算する。軸のスコアと同じ枠組みで、
**結果が最も予測しづらい 1 手** = 二値エントロピー `H(p, 1−p)` が最大になる値、
つまりシェアが 1/2 に最も近い値を採る。候補は画面に出ている値だけ
(見せていない値を推薦するのは、悪い一手を推薦するより悪い罠になる)。
同点は小さいバケツ → 名前空間名 → タグ名。**コア側に置いた**のは M4 の UI が
同じ推薦を使えるようにするため — UI が自前でボタンを並べて先頭を勧めれば、
上の挙動をそのまま再現する。実測で 63,901 → 1 が **9 手**(毎手 44% 以上減)。

**決定性は「丸めてから比較」で担保する** — スコアは浮動小数点なので、
比較の前に 1e-6 グリッドへ丸め、同点は整数(カバレッジ → 値の数)、
最後に名前空間名/タグ名に落とす。`log2` / `ln` の最終ビットは
プラットフォームの libm で 1 ulp 違いうるため。
ただしこれは**露出を抑えるのであって同一性の証明ではない**:
真のスコアがグリッド境界をまたいでいれば 1 ulp でも順序は入れ替わりうる。
同一マシン・同一 DB での決定性は厳密で、CLI とテストが主張しているのはそちら。

**マージはしない、を #5 でも維持する** — §6-2 は「本格的なドリルダウンは
issue #5 の範囲なのでそこで一緒に設計する」としていた。設計した結果、
ファセット件数は SQL の集約であり、索引後に作られたファイル(タグを持たない)を
そこへ混ぜると**同じファイルを索引側とライブ側で二重に数える**か、
差分集合の file_id 全件を集約から除外する第 2 の経路を作るかになる。
`sagasu tags` の行の列挙とは違い、件数の集約には足し合わせる意味が保証できない。
よって `sagasu tags` と同じく「照会はするがマージはしない」に留め、
`delta : N changed` と警告で今どれだけ古いかを必ず出す。
増分タグ更新(§6-2 の残論点)が入ればこの論点は消える。

**鮮度の表示規律を型で運ぶ** — `BrowseView::snapshot` が
`tag_scan_generation` と現在の `scan_generation` を持って返るので、
M4 の UI は「これは索引時点のスナップショットである」を受け取らずに
ビューを描画できない。CLI 側の鮮度ブロックは `sagasu tags` と同一の関数
(`sagasu-cli::output::print_tag_freshness`)から出る — 2 つ書いてあれば
片方が古くなるため。

**機械可読出力は CLI ではなくコア API** — M4 の Tauri は Rust なので
`sagasu-core` に直接リンクする(§3)。機械可読インターフェースは
`BrowseQuery` / `BrowseView` そのものであり、CLI に `--json` を足すと
同じ内容を記述する 2 本目の契約を手で同期することになる。
CLI 全体の機械可読出力は issue #6 の論点。

**実測(`/usr`, 63,901 files / 555,664 tag rows, release, `--no-fresh`)**

| 操作 | 所要 |
|---|---|
| `browse`(索引全体) | 1.01s |
| `browse kind:image` | 0.93s |
| (参考)`sagasu tags`(名前空間一覧) | 1.22s |

支配的なのは絞り込み集合そのものの評価で、`file_tags` の主キー順全走査 1 パス。
browse は同じ集合を 3 回読むので 1 回だけ評価して temp テーブルに落とす
(1.27s → 0.93s)。集合評価の索引化は別 issue。

**受け入れシナリオ(`docs/browse.md` §7 に全出力)** — 2 通り測った。
人が「画像」「PNG」「テストデータ」だけを覚えている経路では
`/usr` の「Go のどこかにある zip テストデータの PNG」に
63,901 → 6,203 → 449 → 110 → 2 の **4 ステップ**。
事前知識ゼロで `next :` だけを追う経路では 63,901 → 1 が **9 手**。
いずれもディレクトリ位置(`src/archive/zip/testdata/`)は一度も知らなくてよい。

**CLI の `next :` 行は貼り付けて実行できる形にする** — 既定と違うフラグを
引き継ぎ(`--values` は軸の順位を変え、`--no-fresh` は鮮度確認の有無を変える)、
POSIX シェルクォートを掛ける。`TOKEN_SEPARATORS` に空白が入っている以上
`2024 reports/` は `path:2024 reports` というタグを作るので、
クォートしなければツールが印字したコマンドをツール自身が
`error: tag "reports" is not in namespace:value form` で拒否する。

**表示は「抑制した」と「無かった」を区別する** — `--label-terms 0` /
`--values 0` / `--axes 0` は計算結果を隠すだけであって、
ラベルが無いことでも葉に着いたことでもない。タグ層が無い索引は
`sagasu tags`(引数なし)に揃えて**終了コード 2**(issue #49 で 1→2。
正本は docs/cli.md §6)。スクリプトから叩いたときに「探索するものが無い」を
「空の答えを正常に返した」と混同させないため。

### 6-4. M3 ドリルダウンで残した論点

- **カバレッジの低い名前空間は既定では軸に出ない**。`anomaly:` / `date:` /
  `version:` は residue に潰される。ランキングとしては正しいが「珍しいものを
  見せてほしい」という別の問いには答えない。黙って消してはおらず、
  `(N more axis/axes could narrow this group)` が必ず出る。
  意外性で並べる軸が要るなら別 issue
- **集合評価が毎回 `file_tags` の全走査**。部分索引やタグ集合のビットマップは後続
- **ラベルと共有値リストの重複**。意図的(順位づけ vs 列挙)だが表示は冗長
- **ラベルは同一軸の排他値を同時に並べうる**(`path:renewal` と `path:photos`)。
  c-TF-IDF は語ごとに独立にスコアするので AND とは区別しない。
  各語に `(6/10)` を添えることで読み取れるようにはしてあるが、暗黙の読解に頼っている
- **推薦は貪欲で 1 手先しか見ない**。9 手が最小手数だとは主張していない
- **`next :` のクォートは POSIX シェル前提**。`cmd.exe` では貼り直せない
- **`find --tag` / 全文検索との融合**は未着手。#5 のスコープ外

### 6-5. 埋め込みメタデータ(issue #40 の確定事項)

§6-2 で後続へ分離した「Office プロパティ・PDF info・EXIF」を実装した。実装は
`sagasu-core::docmeta`(3系統のパーサ)で、`tags` からは `FileFacts.embedded` という
**ただのデータ**として見える。

**読むのは tagindex、判断するのは tags** — 決定性は §6-1 の「型で守る」をそのまま維持する。
`tags::tags_for` は相変わらずファイルシステムに触れない。実行ごとに揺れうる正規化
(作者の順序・日付の粒度)は `docmeta` 側で済ませてから渡す。作者は**ソート+重複排除済み**、
日付は `YYYY-MM-DD` に還元済み。

**名前空間** — `author:` / `title:` / `camera:`、および `date:` への追加。
`dc:creator` と `cp:lastModifiedBy` は**同じ `author:` に入れる**。「山田が触った文書」は
1つの問いであって、役割ごとに名前空間を割るとその答えが二分されるだけだから。
`date:` は名前由来と同じく**日を落として** `YYYY` と `YYYY-MM` の2粒度(§6-1 の
`patterns::date_values` をそのまま通す)。1日1バケツの軸は辿れない。

**メタデータが無いのは失敗ではない** — EXIF の無い JPEG も `dc:title` が空の docx も
普通にある。壊れたコンテナだけを failed に数える。実データの大半が前者なので、
混ぜると「失敗」の隣に五桁の数字が並んで誰も見なくなる。

**`sagasu tag` は分母も出す** — `embedded meta: N candidates, M with metadata, K failed`。
`magic bytes` 行と同じ理由で、「`author:` 軸が実際どれだけ埋まっているか」は
タグ件数からは読めない。failed は**パスと理由**を先頭数件そのまま出す。

## 7. スキーマ v0 の布石

後付けが痛い(全ファイル再走査になる)3点を v0 から持つ:

1. **コンテンツハッシュ(BLAKE3)**: 重複検出、リネーム・移動の追跡、退避後の同一性検証。サイズ閾値以下は即時、以上は遅延計算
2. **安定ファイル ID**: パスとは独立した ID。ハッシュ+メタデータで同一ファイルを追跡し、リネーム・移動でタグ・履歴が切れない。ローカルから退避された後も台帳エントリとして残せる
3. **アクセス履歴**: NTFS の last-access は既定で信頼できないため、USN Journal のイベントや自前観測で「最終アクセス」を記録。コールド判定(§9)の基盤

## 8. プラグイン境界(embedding / LLM)

コアは決定的・オフラインを守り、意味推論の強化は明示的なオプトインレイヤーとする。

- **embedding プラグイン**: ローカルモデル(GPU 機なら multilingual-e5 / ruri 系)or API。sqlite-vec に格納し、ハイブリッド検索(キーワード + ベクトル、RRF 融合)を解放
- **LLM タグ付けプラグイン**: 新規・更新ファイルのみ/クラスタ代表点のみ等の絞り込み前提。タグ語彙は既存タグ集合に寄せて発散を防ぐ
- 境界の形(トレイト/サブプロセス/外部コマンド)は未決。CLI として「タグを stdin/stdout で受け渡す外部コマンド協調」が最も疎で OSS 的には筋が良さそう

## 9. 将来構想: ストレージティアリングサービス

「ほとんど参照されないが数年の保存義務があるファイル」を、ローカル台帳(sagasu のインデックス)を根拠に AWS の低頻度アクセスストレージ(S3 Glacier 系)へ退避する商用サービス。

- sagasu OSS = 資産台帳(inventory)。ハッシュ・安定ID・アクセス履歴(§7)がそのまま移行判定と同一性検証の基盤になる
- 退避後もローカル台帳にエントリが残り、検索にヒットする(「ここにあったが、今はアーカイブにある」)
- 本体はコアのスコープ外。ただしスキーマとコールド判定はコアで成立させる

## 11. 未決事項 (open questions)

- ~~tantivy vs SQLite FTS5 の最終判断(ベンチ条件と規模の定義)~~ → **tantivy 継続で回答済み**
  (issue #35)。比較実装は `prototypes/proto-ftcompare`(3エンジンが同一の走査・同一の本文抽出・
  同一アナライザを共有する使い捨てプロトタイプ)、ベンチ設定は `bench/configs/ftcompare-linux.toml`。
  **Linux コンテナでの計測なので絶対値は Windows 実機と別物** — 有効なのはエンジン間の比だけ。
  10万ファイル(`bench gen --files 100000 --seed 42`、索引対象 97,168 文書 / 本文 5,690 MiB)での実測:

  | | tantivy | FTS5(Lindera→unicode61) | FTS5(trigram) |
  |---|---|---|---|
  | 索引構築 | **148.9s** | 488.5s | 415.8s |
  | 索引サイズ(索引のみ) | **1,112 MiB**(本文の 0.195) | 1,536 MiB(0.270) | 8,072 MiB(1.419) |
  | 単語クエリ p50 | **2.6〜3.3ms** | 3.3〜3.4ms | 80〜127ms |
  | フレーズクエリ p50 | **19〜21ms** | 45〜49ms | 212ms |
  | 1文書だけ差分更新 p50 | 80.3ms | **13.3ms** | 14.6ms |
  | 日本語2文字クエリ(「性能」) | 一致 | 一致 | **0件(エラーにならない)** |

  - **trigram は日本語用途では失格**。部分一致なので適合率は完璧(後述の「全文検索」で 1.00)だが、
    **3文字未満のクエリがエラーにもならず 0 件で返る**。「性能」「測定」が引けない
  - **依存の重さは判断材料にならない**。分かち書きが要る以上 IPADIC(57MB)は FTS5 側でも同じで、
    避けられるのは trigram だけ。その trigram が上記で落ちる
  - **FTS5 が勝つのは「1文書ずつコミットする」形の更新だけ**(6倍)。まとめて入れると
    tantivy 1.53ms/文書 に対し FTS5 5.03ms/文書 で逆転する。§5 の再走査ベースの更新は後者の形なので、
    この一点で FTS5 を採る理由にはならない
  - 検索品質は grep 全数との突き合わせで確認済み。トークナイザが同じなので tantivy と
    FTS5(Lindera)は同じ振る舞いをする — 再現率はどちらも 1.00 だが、
    クエリが一般語に分割されると適合率が落ちる(「全文検索」→ 全文/検索 で適合率 0.0003)。
    これは**エンジンの差ではなくトークナイザの性質**で、どちらを選んでも同じ
  - ただし **tantivy は大きな文書でフレーズの位置情報を落とす**: 10万規模の "delta merge" で
    7,024 件中 158 件(2.25%)取りこぼした(FTS5 側は 0)。単語一致は正しいので位置だけの問題。
    再現手順は issue #35 の PR に記録済みで、別 issue で追う
